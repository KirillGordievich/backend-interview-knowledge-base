# SQL — Транзакции и ACID

## Что такое транзакция?

Транзакция — это группа операций, которая выполняется как единое целое: либо все операции применяются, либо ни одна. Классический пример — перевод денег между счетами. Нельзя списать с одного счёта и не зачислить на другой:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- применить все изменения
-- ROLLBACK; — отменить всё, если что-то пошло не так
```

---

## Что такое ACID?

ACID — четыре свойства, которые гарантируют надёжность транзакций.

### Atomicity (атомарность)

Транзакция выполняется полностью или не выполняется совсем. Если посередине транзакции происходит сбой — все изменения откатываются. Не бывает ситуации, когда деньги списались с одного счёта, но не пришли на другой.

### Consistency (согласованность)

Каждая успешная транзакция переводит базу из одного корректного состояния в другое. Все ограничения целостности (CHECK, FK, UNIQUE, NOT NULL) соблюдаются. Если транзакция нарушает какое-то ограничение — она откатывается.

### Isolation (изолированность)

Параллельные транзакции не должны мешать друг другу. На практике полная изоляция стоит дорого, поэтому существуют разные уровни изоляции — компромисс между корректностью и производительностью. Подробнее ниже.

### Durability (надёжность)

После получения подтверждения COMMIT данные сохранены навсегда — даже при отключении питания или сбое оборудования. PostgreSQL гарантирует это за счёт WAL-журнала (Write-Ahead Log): прежде чем изменить данные на диске, запись об изменении попадает в журнал.

## Какие бывают аномалии при параллельном доступе?

Когда несколько транзакций работают одновременно, могут возникать аномалии — ситуации, которых не было бы при последовательном выполнении.

### Dirty Read (грязное чтение)

Транзакция читает данные, которые другая транзакция изменила, но ещё не закоммитила. Проблема в том, что та транзакция может сделать ROLLBACK — и тогда мы прочитали данные, которых «никогда не существовало».

```sql
T1: UPDATE accounts SET balance = 0 WHERE id = 1;
T2: SELECT balance FROM accounts WHERE id = 1;  -- видит 0 (незафиксировано!)
T1: ROLLBACK;
-- T2 прочитала баланс 0, хотя реально он не менялся
```

В PostgreSQL dirty read невозможен даже на самом слабом уровне изоляции.

### Non-repeatable Read (неповторяемое чтение)

Два одинаковых SELECT внутри одной транзакции возвращают разные результаты для одной и той же строки. Это происходит потому, что между чтениями другая транзакция успела изменить данные и закоммитить.

```sql
T1: SELECT balance FROM accounts WHERE id = 1;  -- 1000
T2: UPDATE accounts SET balance = 500 WHERE id = 1; COMMIT;
T1: SELECT balance FROM accounts WHERE id = 1;  -- 500 (изменилось!)
```

Отличие от dirty read: тут мы читаем закоммиченные данные, но они изменились между чтениями.

### Phantom Read (фантомное чтение)

Похоже на non-repeatable read, но речь не об изменении строки, а о появлении новых строк. Повторный запрос с тем же WHERE возвращает другой набор строк, потому что другая транзакция вставила или удалила подходящие строки.

```sql
T1: SELECT * FROM orders WHERE status = 'new';  -- 5 строк
T2: INSERT INTO orders (status) VALUES ('new'); COMMIT;
T1: SELECT * FROM orders WHERE status = 'new';  -- 6 строк (откуда взялась?!)
```

### Serialization Anomaly (аномалия сериализации)

Результат параллельного выполнения транзакций не соответствует ни одному возможному порядку их последовательного выполнения. Самый коварный тип аномалии — каждая транзакция по отдельности делает всё правильно, но вместе они дают невозможный результат.

```sql
-- Обе транзакции читают текущую сумму и вставляют строку
T1: SELECT SUM(amount) FROM transactions;  -- 100
T2: SELECT SUM(amount) FROM transactions;  -- 100
T1: INSERT INTO transactions (amount) VALUES (100); COMMIT;
T2: INSERT INTO transactions (amount) VALUES (100); COMMIT;
-- Последовательно: одна увидела бы 100, вторая — 200
-- Параллельно: обе увидели 100 — такого не может быть ни в каком порядке
```

## Какие бывают уровни изоляции

Уровень изоляции определяет, какие аномалии транзакция готова терпеть. Чем строже уровень — тем меньше аномалий, но тем выше цена.

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- или прямо при старте транзакции:
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

### Какие аномалии допускает каждый уровень изоляции

| Уровень | Dirty Read | Non-repeatable Read | Phantom Read | Serialization Anomaly |
|---|---|---|---|---|
| READ UNCOMMITTED | Возможно | Возможно | Возможно | Возможно |
| READ COMMITTED | Нет | Возможно | Возможно | Возможно |
| REPEATABLE READ | Нет | Нет | Возможно | Возможно |
| SERIALIZABLE | Нет | Нет | Нет | Нет |

### READ UNCOMMITTED

Самый слабый уровень — транзакция видит незафиксированные изменения других транзакций (dirty read). На практике почти не используется. **PostgreSQL вообще не поддерживает этот уровень** — если указать READ UNCOMMITTED, PostgreSQL молча будет работать как READ COMMITTED.

### READ COMMITTED (PostgreSQL по умолчанию)

Читаем только закоммиченные данные — dirty read невозможен. Но ключевой нюанс PostgreSQL: **каждый отдельный statement получает свой snapshot**, а не вся транзакция целиком.

Что это значит на практике:

```sql
-- Transaction A:
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- видит 1000

-- Transaction B (параллельно):
UPDATE accounts SET balance = 500 WHERE id = 1;
COMMIT;

-- Transaction A (продолжается):
SELECT balance FROM accounts WHERE id = 1;  -- видит 500!
COMMIT;
```

Второй SELECT в транзакции A видит уже обновлённые данные, потому что B успела закоммитить между двумя SELECT-ами. Каждый SELECT берёт свежий snapshot — поэтому повторные чтения могут возвращать разные результаты (non-repeatable read).

Для большинства обычных CRUD-операций это нормально и не создаёт проблем. Именно поэтому PostgreSQL использует этот уровень по умолчанию — он даёт хороший баланс между корректностью и производительностью.

### REPEATABLE READ

Транзакция получает **один snapshot на момент своего начала**, и все последующие SELECT видят согласованное состояние данных — стабильное чтение внутри транзакции.

```sql
-- Transaction A:
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;  -- видит 1000

-- Transaction B (параллельно):
UPDATE accounts SET balance = 500 WHERE id = 1;
COMMIT;

-- Transaction A (продолжается):
SELECT balance FROM accounts WHERE id = 1;  -- всё ещё 1000!
COMMIT;
```

Отличие от READ COMMITTED: там каждый statement видит свежие данные, тут вся транзакция видит одну и ту же картину мира.

**PostgreSQL-особенность:** REPEATABLE READ в PostgreSQL также защищает от phantom read (за счёт MVCC). Это строже, чем требует стандарт SQL — по стандарту phantom read на этом уровне допустим.

Но есть цена: если PostgreSQL обнаружит конфликт, который нельзя корректно разрешить (например, две транзакции пытаются обновить одну строку), он завершит транзакцию ошибкой:

```
ERROR: could not serialize access due to concurrent update
```

Приложение должно поймать эту ошибку и повторить транзакцию (retry loop).

### SERIALIZABLE

Самый строгий уровень. Гарантирует, что результат параллельного выполнения транзакций эквивалентен какому-то последовательному порядку. Но это **не значит**, что транзакции буквально выполняются одна за другой.

PostgreSQL реализует это через **SSI (Serializable Snapshot Isolation)** — транзакции работают параллельно, но PostgreSQL отслеживает зависимости между ними. Если обнаруживается опасный конфликт (цикл зависимостей), одна из транзакций получает serialization failure:

```sql
-- Transaction A:
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT SUM(amount) FROM transactions;  -- видит 100
INSERT INTO transactions (amount) VALUES (100);

-- Transaction B (параллельно):
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT SUM(amount) FROM transactions;  -- тоже видит 100
INSERT INTO transactions (amount) VALUES (100);

-- Одна из транзакций получит:
-- ERROR: could not serialize access due to read/write dependencies
-- Приложение должно сделать retry
```

Если бы транзакции выполнялись последовательно, вторая увидела бы уже 200 (после вставки первой). Но обе увидели 100 — такого не могло бы быть при любом последовательном порядке, поэтому PostgreSQL откатывает одну из них.

### Почему не использовать SERIALIZABLE всегда?

Потому что это дороже:
- Больше overhead — SSI отслеживает зависимости, что требует дополнительной памяти и CPU
- Больше serialization failure — транзакции чаще откатываются
- Нужен retry в приложении — каждый вызов БД должен уметь повторяться
- Меньше throughput при высокой конкуренции

Для большинства задач READ COMMITTED + явные механизмы (row locks через `SELECT FOR UPDATE`, atomic UPDATE с WHERE-условиями) дают достаточную корректность без лишних накладных расходов. SERIALIZABLE стоит выбирать для конкретных критичных операций, а не как дефолт для всего приложения.

## Как PostgreSQL реализует изоляцию?

### Как работает MVCC

PostgreSQL не блокирует строки при чтении. Вместо этого каждая транзакция работает со своим snapshot данных — это и есть MVCC.

Как это работает: каждая строка в таблице хранит две скрытые метки — `xmin` (ID транзакции, которая создала строку) и `xmax` (ID транзакции, которая удалила или обновила строку). Когда транзакция делает UPDATE, она не перезаписывает строку, а создаёт новую версию, помечая старую как удалённую.

Благодаря этому читатели не блокируют писателей и наоборот — каждый видит свою версию данных. Устаревшие версии строк, которые уже не нужны ни одной транзакции, очищает процесс VACUUM.

### В чём разница между пессимистичным и оптимистичным подходом

| Подход | Как работает | Пример |
|---|---|---|
| **Пессимистичный** (блокировки) | Блокировать данные перед изменением | `SELECT FOR UPDATE` |
| **Оптимистичный** (MVCC) | Работать с snapshot, проверять конфликты при COMMIT | REPEATABLE READ, SERIALIZABLE |

На практике часто используют комбинацию: оптимистичный подход как основу (MVCC) и точечные пессимистичные блокировки (`SELECT FOR UPDATE`) для критичных операций.

## SAVEPOINT — частичный откат транзакции

Иногда нужно откатить часть транзакции, не отменяя всё остальное. Для этого есть SAVEPOINT — именованные точки внутри транзакции, к которым можно вернуться:

```sql
BEGIN;
INSERT INTO orders (id, total) VALUES (1, 100);

SAVEPOINT sp1;
INSERT INTO order_items (order_id, qty) VALUES (1, 5);
-- Ошибка! Откатываем до savepoint
ROLLBACK TO sp1;

-- Продолжаем транзакцию — order всё ещё создан
INSERT INTO order_items (order_id, qty) VALUES (1, 3);
COMMIT;  -- order создан, item с qty=3 сохранён
```

## Вопросы на собеседовании

**Какой уровень изоляции по умолчанию в PostgreSQL и почему?**
READ COMMITTED. Каждый отдельный statement в транзакции видит данные, зафиксированные на момент начала именно этого statement-а (не транзакции). Два SELECT в одной транзакции могут вернуть разные данные, если между ними кто-то закоммитил изменения. Для большинства CRUD-операций это нормально и даёт лучший баланс между корректностью и производительностью.

**В чём ключевая разница между READ COMMITTED и REPEATABLE READ?**
В гранулярности snapshot-а. READ COMMITTED берёт свежий snapshot на каждый statement — повторный SELECT может вернуть новые данные. REPEATABLE READ берёт один snapshot на всю транзакцию — все SELECT видят одну и ту же картину мира, даже если другие транзакции закоммитили изменения.

**Чем REPEATABLE READ отличается от SERIALIZABLE?**
REPEATABLE READ фиксирует snapshot на момент начала транзакции — все чтения стабильны. Но возможны аномалии сериализации (write skew): две транзакции читают одни данные, на основе прочитанного делают разные записи, и результат нарушает инвариант. SERIALIZABLE гарантирует, что результат эквивалентен какому-то последовательному порядку — если это невозможно, одна из транзакций откатывается.

**SERIALIZABLE значит что транзакции выполняются последовательно?**
Нет. PostgreSQL использует SSI (Serializable Snapshot Isolation) — транзакции работают параллельно, но система отслеживает зависимости между ними. Если обнаруживается цикл зависимостей (результат невозможен ни при каком последовательном порядке), одна из транзакций получает serialization failure. Приложение должно уметь делать retry.

**Что такое MVCC?**
Multi-Version Concurrency Control — механизм, при котором каждая транзакция работает со своим snapshot данных. Каждая строка имеет метки `xmin`/`xmax` — какая транзакция её создала и удалила/обновила. Благодаря этому читатели не блокируют писателей и наоборот. Устаревшие версии строк очищает VACUUM.

**Что произойдёт при конфликте на REPEATABLE READ?**
Если две транзакции на REPEATABLE READ пытаются обновить одну строку — вторая получит ошибку `could not serialize access due to concurrent update`. Приложение должно поймать ошибку и повторить транзакцию (retry loop).

**Почему не использовать SERIALIZABLE всегда?**
Больше overhead (SSI отслеживает зависимости), больше serialization failure и вынужденных retry, меньше throughput при высокой конкуренции. Для большинства задач READ COMMITTED + явные механизмы (`SELECT FOR UPDATE`, atomic UPDATE с WHERE-условием) дают достаточную корректность. SERIALIZABLE стоит выбирать точечно для критичных операций, а не как дефолт.

**Что такое write skew?**
Аномалия при REPEATABLE READ: две транзакции читают одни данные, на основе прочитанного делают разные записи, и результат нарушает инвариант. Пример: два врача проверяют «есть ли хотя бы один дежурный» и оба снимают себя с дежурства. Каждый видел что дежурный есть (другой врач), но в итоге дежурных ноль. Защита: SERIALIZABLE или явные блокировки.
