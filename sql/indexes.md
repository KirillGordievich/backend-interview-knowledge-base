# SQL — Индексы

## Что такое индекс

Индекс — вспомогательная структура данных для быстрого поиска строк в таблице без полного перебора (seq scan).

**Плюсы:** ускоряет SELECT, ORDER BY, JOIN.
**Минусы:** замедляет INSERT, UPDATE, DELETE — при каждом изменении индексируемого поля индекс тоже обновляется.

---

## Какие типы индексов по структуре данных есть в PostgreSQL

По умолчанию PostgreSQL создаёт B-Tree. Остальные нужно указывать явно через `USING`.

### B-Tree (по умолчанию)

Сбалансированное дерево. Подходит для большинства задач — поиск по равенству, диапазоны, сортировка.

```sql
CREATE INDEX idx_users_email ON users(email);  -- неявно USING btree
CREATE INDEX idx_orders_created ON orders(created_at DESC);
```

Работает с операторами: `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, `IN`, `IS NULL`, `LIKE 'foo%'`.

### Hash

Хранит хеш значения. Быстрее B-Tree для точного совпадения (`=`), но не поддерживает диапазоны и сортировку.

```sql
CREATE INDEX idx_sessions_token ON sessions USING hash(token);
```

На практике используется редко — B-Tree почти всегда не хуже, а умеет больше.

### GIN (Generalized Inverted Index)

Инвертированный индекс — подходит для типов, где одно значение содержит несколько ключей: массивы, `jsonb`, полнотекстовый поиск. Для каждого элемента хранит список строк, где он встречается.

```sql
-- Поиск по элементу массива
CREATE INDEX idx_posts_tags ON posts USING gin(tags);
SELECT * FROM posts WHERE tags @> ARRAY['python'];

-- Поиск по JSONB
CREATE INDEX idx_events_data ON events USING gin(data);
SELECT * FROM events WHERE data @> '{"type": "click"}';

-- Полнотекстовый поиск
CREATE INDEX idx_articles_body ON articles USING gin(to_tsvector('russian', body));
SELECT * FROM articles WHERE to_tsvector('russian', body) @@ to_tsquery('python');
```

GIN медленнее обновляется чем B-Tree (запись дороже), зато очень быстро ищет.

### GiST (Generalized Search Tree)

Расширяемое дерево для нестандартных типов: геометрия, диапазоны (`tsrange`, `int4range`), географические данные (PostGIS). Поддерживает пересечение, вхождение, близость.

```sql
-- Пересечение диапазонов дат (например, бронирования)
CREATE INDEX idx_bookings_period ON bookings USING gist(period);
SELECT * FROM bookings WHERE period && '[2024-01-01, 2024-01-10]'::tsrange;
```

### BRIN (Block Range Index)

Хранит не каждое значение, а диапазон значений для блока страниц. Очень маленький (килобайты вместо гигабайт), но работает только если данные физически упорядочены — то есть значение колонки коррелирует с позицией строки на диске.

```sql
-- Хорошо для монотонно растущих данных: created_at, id serial
CREATE INDEX idx_logs_created ON logs USING brin(created_at);
```

Идеален для огромных append-only таблиц (логи, события), где B-Tree был бы слишком большим.

---

### Когда что использовать

| Тип | Когда |
|---|---|
| **B-Tree** | Почти всегда — равенство, диапазоны, сортировка |
| **Hash** | Только точное `=`, очень высокий throughput вставок (редко нужен) |
| **GIN** | Массивы, JSONB, полнотекстовый поиск |
| **GiST** | Диапазоны, геометрия, PostGIS |
| **BRIN** | Огромные таблицы с монотонными данными (логи, события) |

## Какие виды индексов бывают

| Вид | Описание |
|---|---|
| INDEX (обычный) | Ускоряет поиск по столбцу |
| UNIQUE INDEX | Запрещает дубликаты в индексируемом столбце |
| PRIMARY KEY | Уникальный индекс без NULL, один на таблицу |
| FULLTEXT INDEX | Полнотекстовый поиск в CHAR/VARCHAR/TEXT |
| Частичный (INDEX … WHERE …) | Индекс только по подмножеству строк |

```sql
-- Обычный
CREATE INDEX idx_users_email ON users(email);

-- Уникальный
CREATE UNIQUE INDEX idx_users_login ON users(login);

-- Частичный — индексирует только неактивных клиентов
CREATE INDEX idx_customer_inactive ON customer(active) WHERE active = 0;
```

## В чём разница между кластерным и некластерным индексом

| | Кластерный (Clustered) | Некластерный (Non-Clustered) |
|---|---|---|
| Физический порядок строк | Определяет | Не влияет |
| Количество на таблицу | Один | Несколько |
| Перестроение таблицы | Требуется при создании | Не требуется |

**Кластерный индекс** — строки данных физически упорядочены на диске по значениям индекса. Диапазонные запросы (BETWEEN, >) по нему очень быстры.

## Когда планировщик не использует индекс

- **Низкая кардинальность** — если значение встречается в большинстве строк (например, `active = true` у 95%), seq scan дешевле
- **Протухшая статистика** — после массового DELETE/INSERT статистика ещё не пересчитана. Планировщик принимает решение на старых данных (индекс содержит ссылки на удалённые строки). Решение: `ANALYZE`
- **LIKE с ведущим символом** — `LIKE '%foo'` никогда не использует индекс; `LIKE 'foo%'` — использует
- **Функция над столбцом** — `WHERE upper(name) = 'ALICE'` не использует индекс по `name`. Решение — функциональный индекс:
  ```sql
  CREATE INDEX idx_users_name_upper ON users(upper(name));
  ```
- **Неявное преобразование типов** — сравнение `int_col = '42'` (число vs строка) может заблокировать использование индекса

## Что показывает EXPLAIN и EXPLAIN ANALYZE

`EXPLAIN` показывает план выполнения запроса — какие операции планировщик выбрал. `EXPLAIN ANALYZE` делает то же, но **реально выполняет запрос** и показывает фактическое время и количество строк:

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;
```

**Что смотреть:**

| Параметр | Что означает |
|---|---|
| `Seq Scan` | Полный перебор таблицы — подозрительно на больших таблицах |
| `Index Scan` | Использован индекс |
| `cost=X..Y` | Оценка стоимости: X — до первой строки, Y — полная стоимость |
| `actual time` | Реальное время выполнения (только в ANALYZE) |
| `rows` | Оценка vs реальное кол-во строк; большое расхождение → проблема со статистикой |
| `loops` | Сколько раз выполнялся узел; `loops × rows` — реальный объём работы |

## Какой индекс ты бы предложила для этого запроса? Почему именно в таком порядке расположишь поля индекса?

Представь таблицу:

```sql
orders (
    id,
    user_id,
    status,
    created_at,
    amount
)
```

И очень часто выполняется запрос:

```sql
SELECT *
FROM orders
WHERE user_id = 123
  AND status = 'completed'
ORDER BY created_at DESC
LIMIT 20;
```

Я бы соделал индекс

```sql
CREATE INDEX idx_orders_user_status_created
ON orders (user_id, status, created_at DESC);
```

Чтобы сначала сократить поиск по ордерам конкретного юзера, потом выбрать ордера только с нужным статусом, а потом сразу бы получил отсортированный список нужны ордеров, просто взяв 20 первых ордеров.
