# System Design — Базовый подход

## Первый шаг: выяснить требования

Не начинать рисовать архитектуру сразу. Сначала задать вопросы и зафиксировать входные данные. Интервьюер специально даёт расплывчатую задачу — он хочет увидеть, что ты умеешь уточнять.

### Что спрашивать

**1. Функциональные требования — что система должна делать:**
- Какие операции? (приём данных, чтение, агрегация, алерты?)
- Кто потребитель? (пользователи через UI, другие сервисы, аналитики?)
- Какие API нужны? (REST, gRPC, WebSocket?)

**2. Входные данные — что именно приходит:**
- Сколько источников данных? (1000 агентов? 1 млн пользователей?)
- Как часто отправляют данные? (раз в 10 секунд? раз в минуту?)
- Какой размер одного запроса? (100 байт? 10 КБ? 1 МБ?)
- Какая структура данных? (JSON с 5 полями? бинарный blob?)

**3. Нефункциональные требования:**
- Допустимая задержка? (real-time? допустимо 5 минут?)
- Допустима ли потеря данных? (at-least-once? exactly-once?)
- Сколько хранить? (7 дней? год? навсегда?)
- Availability vs consistency?

## Второй шаг: расчёт нагрузки (Back-of-the-Envelope)

Это обязательная часть. Без расчётов невозможно обосновать выбор технологий.

### Пример: 1000 агентов отправляют метрики раз в 10 секунд

**RPS (Requests Per Second):**

```
1000 агентов / 10 секунд = 100 RPS
```

100 RPS — это немного. Один сервер спокойно справится.

**Размер данных — нужно уточнить у интервьюера.** Допустим, одна метрика:

```json
{
  "agent_id": "agent-042",
  "timestamp": 1695000000,
  "cpu": 45.2,
  "memory": 78.1,
  "disk": 62.0,
  "network_in": 1024000,
  "network_out": 512000
}
```

Примерно ~200 байт на запрос.

**Объём данных в сутки:**

```
100 RPS × 200 байт = 20 КБ/сек
20 КБ/сек × 86400 сек = ~1.7 ГБ/день
```

**В месяц:** ~50 ГБ. **В год:** ~600 ГБ.

Это помогает понять:
- Нужен ли шардинг? (600 ГБ/год — скорее нет)
- Нужна ли очередь? (100 RPS — скорее нет, но может быть нужна для надёжности)
- Какую БД выбрать? (time-series данные → ClickHouse, TimescaleDB, InfluxDB)

### Шаблон расчёта

```
1. RPS = количество_источников / интервал_отправки
2. Пропускная способность = RPS × размер_запроса
3. Хранилище/день = пропускная_способность × 86400
4. Хранилище/месяц = хранилище/день × 30
5. Пиковая нагрузка = RPS × 2-3 (запас на пики)
```

### Полезные величины для прикидок

| Что | Сколько |
|---|---|
| 1 день | ~86 400 секунд (~100K) |
| 1 месяц | ~2.5 млн секунд |
| 1 год | ~30 млн секунд |
| 1 КБ | ~1000 байт |
| 1 МБ | ~1 000 000 байт |
| 1 ГБ | ~1 000 000 000 байт |

### Ориентиры по RPS

| RPS | Масштаб |
|---|---|
| 10-100 | Один сервер справится |
| 100-1000 | Может понадобиться оптимизация, кэширование |
| 1K-10K | Load balancer, несколько инстансов |
| 10K-100K | Шардинг, очереди, серьёзная архитектура |
| 100K+ | Распределённые системы, CDN, edge computing |

## Третий шаг: High-Level Design

Только после расчётов рисовать архитектуру. Начинать с основных компонентов, потом детализировать.

Пример для задачи с метриками:

```
Agents (1000)
    │
    ▼
Load Balancer
    │
    ▼
Collector Service (принимает метрики)
    │
    ├──→ Message Queue (Kafka) — буферизация
    │         │
    │         ▼
    │    Writer Service — пишет в БД
    │         │
    │         ▼
    │    TimescaleDB / ClickHouse (хранение)
    │
    └──→ Alerting Service (проверяет пороги в реальном времени)

Dashboard
    │
    ▼
Query Service → БД (агрегации для отображения)
```

## Четвёртый шаг: Deep Dive

Интервьюер выберет одну-две части и попросит углубиться. Типичные вопросы:

- **Как обрабатывать пики?** — очередь (Kafka/RabbitMQ) как буфер между приёмом и записью
- **Что если сервис упал?** — ретраи на стороне агентов, at-least-once delivery, идемпотентность записи
- **Как хранить time-series?** — партиционирование по времени, TTL для автоочистки, downsampling старых данных
- **Как масштабировать?** — горизонтальное масштабирование collector'ов за load balancer'ом, шардинг БД по agent_id

## Частые ошибки на System Design

- **Не уточнять требования** — сразу рисовать архитектуру без понимания масштаба
- **Не считать RPS и объём данных** — невозможно обосновать выбор технологий
- **Overengineering** — ставить Kafka и шардинг для 100 RPS
- **Забывать про failure scenarios** — что если сервис/БД/сеть упали
- **Не обсуждать trade-offs** — у каждого решения есть плюсы и минусы, интервьюер хочет видеть что ты их понимаешь
