# Blockchain — Криптография

## Хеш-функции

**Хеш-функция** — математическая функция, преобразующая данные произвольной длины в строку фиксированной длины.

```
SHA-256("hello") = 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
SHA-256("hellо") = полностью другое значение  ← эффект лавины
```

### Требования к криптографической хеш-функции

| Требование | Описание |
|---|---|
| **Детерминированность** | Одинаковые входные данные → всегда одинаковый хеш |
| **Быстрота вычисления** | Хеш вычисляется эффективно |
| **Необратимость** | По хешу невозможно восстановить исходные данные (pre-image resistance) |
| **Устойчивость к коллизиям** | Невозможно найти два разных входа с одинаковым хешем |
| **Эффект лавины** | Изменение 1 бита входа → полностью другой хеш (~50% бит меняется) |
| **Фиксированная длина** | Выход всегда одинакового размера (SHA-256 → 256 бит) |

### Хеш-функции в блокчейне

| Функция | Выход | Используется |
|---|---|---|
| **SHA-256** | 256 бит | Bitcoin (майнинг, хеширование блоков) |
| **Keccak-256** | 256 бит | Ethereum (адреса, selector функций, подписи) |
| **SHA-3** | 256/512 бит | NIST-стандарт (схожий с Keccak, но не идентичный) |
| **RIPEMD-160** | 160 бит | Bitcoin-адреса (SHA-256 → RIPEMD-160) |

**Ethereum-адрес из публичного ключа:**
```
privateKey → ECDSA → publicKey (64 байта, без префикса 04)
           → Keccak-256(publicKey) → 32 байта
           → последние 20 байт → адрес (0x...)
```

### Merkle Tree

**Merkle Tree** — бинарное дерево хешей. Используется для эффективной проверки вхождения элемента в набор без хранения всего набора.

```
              Root Hash
             /          \
         H(A+B)         H(C+D)
         /    \         /    \
       H(A)  H(B)    H(C)  H(D)
        |     |       |     |
       tx_A  tx_B   tx_C  tx_D
```

**Merkle Proof** — путь от листа до root (логарифмическая длина). Позволяет доказать включение транзакции в блок без скачивания всего блока — используется в light-клиентах.

## Асимметричная криптография

**Асимметричное шифрование (Public Key Cryptography)** — система, в которой пара ключей: публичный (открытый) и приватный (закрытый). Что зашифровано одним — расшифровывается другим.

```
Шифрование:      publicKey  → зашифровать → ciphertext
Расшифрование:   privateKey → расшифровать → plaintext

Подпись:         privateKey → подписать → signature
Верификация:     publicKey  → проверить → true/false
```

### ECDSA (Elliptic Curve Digital Signature Algorithm)

Ethereum использует ECDSA на кривой **secp256k1** (та же, что и Bitcoin).

**Процесс подписи транзакции:**
```
1. Хеш транзакции:  h = keccak256(rlp(tx))
2. Подпись:         (r, s, v) = ECDSA.sign(h, privateKey)
3. Верификация:     publicKey = ECDSA.recover(h, r, s, v)
4. Адрес:           address = keccak256(publicKey)[-20 bytes]
```

**v, r, s** — компоненты подписи:
- `r`, `s` — числа, кодирующие подпись
- `v` — recovery id (27 или 28, в EIP-155 кодирует chainId для защиты от replay)

**`ecrecover`** — встроенная функция Solidity, позволяет восстановить адрес подписанта:
```solidity
bytes32 hash = keccak256(abi.encodePacked(data));
address signer = ecrecover(hash, v, r, s);
require(signer == expectedSigner, "Invalid signature");
```

### Diffie-Hellman и ECDH

**ECDH (Elliptic Curve Diffie-Hellman)** — протокол согласования общего секрета по открытому каналу. Используется в HTTPS-handshake, зашифрованных каналах между кошельками (например, EIP-1024 для шифрованных сообщений).

```
Alice: a (private), A = a×G (public)
Bob:   b (private), B = b×G (public)

Общий секрет:  Alice: a×B = a×b×G
               Bob:   b×A = b×a×G
               → одинаковый результат, не зная приватных ключей друг друга
```

## Zero-Knowledge Proofs (ZKP)

**ZKP (Доказательство с нулевым знанием)** — позволяет доказать знание факта без раскрытия самого факта.

**Классический пример:** доказать, что знаешь пароль от двери в пещере, не показывая пароль.

### Три ключевых свойства

| Свойство | Описание |
|---|---|
| **Completeness (Полнота)** | Если утверждение истинно, честный prover убедит честного verifier |
| **Soundness (Корректность)** | Если утверждение ложно, нечестный prover не сможет убедить verifier |
| **Zero-Knowledge** | Verifier не узнаёт ничего, кроме факта истинности утверждения |

### ZK-SNARKs vs ZK-STARKs

| | ZK-SNARK | ZK-STARK |
|---|---|---|
| Расшифровка | Succinct Non-interactive ARgument of Knowledge | Scalable Transparent ARgument of Knowledge |
| Trusted setup | Требуется (ceremony) | Не требуется |
| Размер proof | Маленький (~200 байт) | Больший (~100 KB) |
| Верификация | Быстрая | Чуть медленнее |
| Квантовая устойчивость | Нет | Да |
| Используется в | Zcash, Groth16, Plonk | StarkWare, STARK-based L2 |

### Применение ZKP в блокчейне

**1. Приватные транзакции (Zcash, Aleo)**
```
Доказываю: "у меня есть 10 токенов и я отправляю 3"
Без раскрытия: адресов, балансов, суммы транзакции
```

**2. ZK-Rollups (Layer 2)**
```
L2 сеть обрабатывает 1000 транзакций
→ генерирует один ZK proof, что все 1000 tx валидны
→ отправляет proof на L1 Ethereum
→ L1 верифицирует proof (дёшево) вместо проверки всех 1000 tx
```

Примеры ZK-Rollups: **zkSync**, **StarkNet**, **Polygon zkEVM**, **Scroll**.

**3. Identity и zkKYC**
```
Доказываю: "мне больше 18 лет" без раскрытия даты рождения
Доказываю: "я гражданин страны X" без раскрытия паспортных данных
```

**4. Верификация вычислений (Verifiable Computation)**
```
Оффчейн вычислю результат сложного алгоритма
→ прикреплю ZK proof, что вычисление корректно
→ смарт-контракт верифицирует proof дёшево, не пересчитывая
```

### Как работает SNARK (упрощённо)

```
1. Программа → Arithmetic Circuit (схема из сложений и умножений)
2. Circuit → R1CS (Rank-1 Constraint System) — система уравнений
3. R1CS → QAP (Quadratic Arithmetic Program) — полиномы
4. Prover использует witness (секретные данные) для генерации proof
5. Verifier проверяет proof математически (без знания witness)
```

**Trusted Setup** — SNARK требует начальной церемонии генерации "токсичных отходов" (toxic waste). Если кто-то сохранит их — сможет генерировать фейковые proofs. **Aleo, Zcash** проводили публичные церемонии с тысячами участников (достаточно, чтобы хотя бы один участник был честным).

## HD Wallets и BIP-32/BIP-39

**Mnemonic (seed phrase)** — 12 или 24 слова, из которых детерминированно генерируются все ключи кошелька.

```
12 слов (128 бит энтропии + 4 бит checksum)
    → BIP-39: words → seed (512 бит, PBKDF2)
    → BIP-32: seed → master key
    → BIP-44: derivation path m/44'/60'/0'/0/0
        44' = BIP-44 purpose
        60' = Ethereum coin type
        0'  = account 0
        0   = external chain
        0   = address index 0
```

```ts
import { ethers } from 'ethers';

// Создание кошелька из мнемоники
const mnemonic = ethers.Mnemonic.fromEntropy(ethers.randomBytes(16));
const wallet = ethers.HDNodeWallet.fromMnemonic(mnemonic);

// Деривация адресов
const child0 = wallet.derivePath("m/44'/60'/0'/0/0");
const child1 = wallet.derivePath("m/44'/60'/0'/0/1");

console.log(child0.address);    // 0x...
console.log(child0.privateKey); // 0x...
```

**Важно:** mnemonic = полный контроль над всеми адресами. Никогда не передавать никому.
