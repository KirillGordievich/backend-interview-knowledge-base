# Blockchain — Консенсус

## Зачем нужен консенсус

**Проблема:** В децентрализованной сети без доверенного центра тысячи нод должны прийти к единому соглашению о состоянии системы.

**Проблема Byzantine Fault Tolerance (BFT):** Консенсус должен работать даже если часть участников ведёт себя злонамеренно или падает.

---

## Proof of Work (PoW)

**PoW** — механизм, в котором право создать блок получает тот, кто первым решил вычислительно сложную задачу (майнинг).

**Задача:** найти `nonce` такой, что `SHA-256(blockHeader + nonce) < target`.

```
target — число, чем меньше target, тем сложнее задача (difficulty)
difficulty корректируется каждые 2016 блоков в Bitcoin (~2 недели)
чтобы среднее время блока оставалось ~10 минут
```

**Свойства:**
- Найти решение: дорого (вычисления, электроэнергия)
- Проверить решение: дёшево (одна хеш-операция)
- Атака 51% — нужно контролировать >50% хешрейта сети

**Проблемы:**
- Огромный расход энергии
- Централизация майнинга (ASIC-пулы)
- Медленная финальность (Bitcoin — ~6 подтверждений = ~1 час)

---

## Proof of Stake (PoS)

**PoS** — право создать блок пропорционально застейканной (заблокированной) сумме токенов.

**Ethereum PoS (после The Merge, сентябрь 2022):**

```
Validator = 32 ETH стейк + ключи + нода

Эпоха (epoch) = 32 слота × 12 секунд = 6.4 минуты
Слот (slot)   = 12 секунд — время для одного блока

На каждый слот:
  1. Протокол выбирает Proposer (RANDAO)
  2. Proposer строит и предлагает блок
  3. Случайный комитет (~128 validators) аттестует блок
  4. При >2/3 голосов → блок принят
```

**Штрафы (Slashing):**
- За двойную подпись (equivocation) — штраф 1–100% стейка + исключение
- За офлайн — небольшой штраф (inactivity leak)

**Преимущества перед PoW:**
- ~99.95% меньше энергии
- Более быстрая финальность
- Экономические стимулы против атак (рискуешь своим стейком)

---

## Finality (Финальность)

**Finality** — гарантия того, что транзакция не может быть отменена.

| Тип | Описание | Пример |
|---|---|---|
| **Probabilistic** | С каждым блоком вероятность отмены падает | Bitcoin: 6 блоков ≈ необратимо |
| **Economic** | Откат экономически нецелесообразен (потеря стейка) | Ethereum PoS |
| **Absolute** | Математически невозможен откат после финализации | Ethereum Casper FFG |

**Ethereum Finality:**
```
Checkpoint (каждые 32 слота) → Justified → Finalized
Для Finalized нужно 2 эпохи (~12.8 минут)
После Finalized: откат требует >1/3 всего стейка (~11 млн ETH) → slashing
```

**Safe Head vs Finalized:**
- `latest` — последний блок (может быть реорганизован)
- `safe` — маловероятно быть реорганизован
- `finalized` — экономически финализирован (~12 мин назад)

## Другие механизмы консенсуса

### DPoS (Delegated Proof of Stake)

Токенхолдеры голосуют за делегатов, которые производят блоки. Используется в EOS, TRON.

- Высокая пропускная способность (~3000 TPS у EOS)
- Централизация (21 BP в EOS)

### PBFT (Practical Byzantine Fault Tolerance)

Классический BFT-алгоритм. Работает при <1/3 злонамеренных нод. Используется в Hyperledger, некоторых PoS-реализациях.

- Детерминированная финальность (сразу)
- Плохо масштабируется при большом числе нод (O(n²) сообщений)

### Tendermint / CometBFT

BFT-консенсус с раундами голосования. Используется в Cosmos, Celestia.

```
Propose → Prevote → Precommit → Commit
Финальность после каждого блока (не вероятностная)
```

### Avalanche Consensus

Опрашивает случайную выборку нод многократно, пока не достигнет уверенного большинства. Очень быстрый, субсекундная финальность.

## Реорганизация блокчейна (Reorg)

**Reorg** — ситуация, когда цепочка переключается на более длинный/тяжёлый fork, отменяя недавние блоки.

```
       ┌── Block 100a (отменён)
99 ── ┤
       └── Block 100b ── Block 101b ← новый canonical fork
```

**В Ethereum PoS:** reorgs на глубину >1-2 блока крайне редки. После Finalization — невозможны.

**Для dApp-разработчиков:** ждать `safe` или `finalized` блок для критических операций.

## Scaling: L2 решения

Ethereum L1 — ~15-20 TPS. Для mass adoption нужно масштабирование.

### Rollups

Выполняют транзакции вне L1 (off-chain), публикуют данные и доказательства на L1.

| | Optimistic Rollups | ZK Rollups |
|---|---|---|
| Доказательство | Fraud proof (challenge period ~7 дней) | Validity proof (мгновенно) |
| Финальность | ~7 дней для вывода на L1 | Несколько часов |
| Совместимость | EVM-совместимы (Arbitrum, Optimism) | ZK-EVM (zkSync, Polygon zkEVM) |
| Стоимость proof | Дёшево генерировать | Дорого генерировать |
| Примеры | Arbitrum, Optimism, Base | zkSync Era, StarkNet, Scroll |

### State Channels

Участники блокируют средства на L1, проводят сотни транзакций off-chain, публикуют финальное состояние. Пример: Lightning Network (Bitcoin), старый Raiden (Ethereum).

### Sidechains

Отдельные блокчейны с мостами к L1. Используют свой консенсус (не наследуют безопасность L1). Пример: Polygon PoS.

### Data Availability (DA)

ZK-Rollups и Optimistic Rollups должны публиковать данные транзакций на L1 для возможности восстановления состояния. Ethereum EIP-4844 (Proto-Danksharding) ввёл **blobs** — дешёвые временные хранилища данных для L2.

## Bridges (Мосты)

**Bridge** — механизм передачи активов между разными блокчейнами.

**Lock & Mint:**
```
1. Залочить токен на Chain A (хранится в смарт-контракте)
2. Замминтить wrapped-токен на Chain B
3. Обратно: сжечь wrapped → разблокировать оригинал
```

**Риски мостов:** самые большие хаки в крипто — атаки на мосты (Ronin Bridge: $625M, Wormhole: $320M).

**Типы мостов:**
- **Trusted/Centralized** — мультисиг или федерация (быстро, есть доверие)
- **Trustless (ZK)** — доказывают состояние исходной цепи через ZK proof (максимальная безопасность)
- **Optimistic** — fraud proof период
