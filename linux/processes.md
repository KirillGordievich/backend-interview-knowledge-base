# Linux — Процессы и сигналы

## Программа vs Процесс

**Программа** — статический исполняемый файл на диске (бинарник, скрипт).
**Процесс** — запущенная программа в памяти. Имеет собственное адресное пространство, стек, файловые дескрипторы, PID.

Один и тот же бинарник может порождать несколько процессов (несколько воркеров nginx).

---

## PID, PPID, создание процессов

- **PID** (Process ID) — уникальный идентификатор процесса
- **PPID** (Parent PID) — PID родительского процесса
- **PID 1** — init/systemd, прародитель всех процессов

### fork() и exec()

**fork()** — создаёт копию текущего процесса (дочерний процесс — копия родителя).
**exec()** — заменяет образ процесса новой программой (не создаёт новый PID).

```bash
# В shell: bash fork → дочерний процесс exec → команда
$ ls    # bash fork()-ует себя, дочерний exec() ls
```

## Специальные виды процессов

### Zombie процесс

Процесс завершился, но родитель ещё не вызвал `wait()` для получения кода завершения. Запись в таблице процессов остаётся, ресурсы освобождены.

```bash
ps aux | grep Z    # состояние Z = zombie
```

Зомби не потребляют CPU/память, но занимают PID. Накопление зомби → невозможно создать новые процессы. Решение: починить родителя или убить его (тогда зомби усыновит init и почистит).

### Orphan процесс (осиротевший)

Родительский процесс завершился раньше дочернего. Дочерний «усыновляется» PID 1 (init/systemd), который вызовет `wait()`.

### Daemon (демон)

Фоновый процесс без управляющего терминала:
- PPID = 1 (init)
- Не привязан к сессии пользователя
- Примеры: sshd, nginx, crond, postgresql

## Команды

```bash
ps aux                          # все процессы (BSD-синтаксис)
ps -ef                          # все процессы с PPID (UNIX-синтаксис)
ps aux --sort=-%cpu | head      # топ по CPU
ps aux --sort=-%mem | head      # топ по памяти

pstree                          # дерево процессов
pstree -p                       # с PID
pstree -p 1234                  # поддерево процесса

pgrep nginx                     # найти PID по имени
pgrep -l nginx                  # PID + имя
pkill nginx                     # послать SIGTERM по имени

top                             # интерактивный мониторинг (q — выход)
htop                            # улучшенный top (F9 — kill, F5 — дерево)
```

## Сигналы

Сигнал — асинхровное уведомление процессу о событии. Процесс может: обработать, проигнорировать, или получить действие по умолчанию.

### Основные сигналы

| Сигнал | Номер | Можно поймать? | Назначение |
|---|---|---|---|
| SIGINT | 2 | Да | Ctrl+C — прерывание из терминала |
| SIGTERM | 15 | Да | Вежливое завершение (по умолчанию `kill`) |
| SIGKILL | 9 | **Нет** | Немедленное уничтожение (ядро убивает напрямую) |
| SIGSTOP | 19 | **Нет** | Приостановить процесс (Ctrl+Z) |
| SIGCONT | 18 | Да | Продолжить приостановленный процесс |
| SIGHUP | 1 | Да | Терминал закрыт / перечитать конфиг (nginx reload) |

### Почему нельзя поймать SIGKILL

SIGKILL обрабатывается ядром, не процессом. Процесс физически не получает управление — ядро принудительно освобождает его ресурсы. Это гарантирует, что любой процесс всегда можно уничтожить.

### Отправка сигналов

```bash
kill 1234            # SIGTERM (15) — вежливое завершение
kill -9 1234         # SIGKILL — немедленное уничтожение
kill -SIGTERM 1234   # то же что kill 1234

kill -1 $(pgrep nginx)    # SIGHUP — перезагрузить конфиг nginx
```

**Правило:** сначала `kill PID` (SIGTERM даёт время на graceful shutdown), если не помогает — `kill -9`.

## PID 1 в Docker

В контейнере PID 1 — ваше приложение (или entrypoint). Это создаёт проблемы:

- PID 1 не имеет стандартных обработчиков сигналов → `docker stop` (SIGTERM) может быть проигнорирован → Docker ждёт 10 секунд → посылает SIGKILL
- PID 1 должен усыновлять и wait()-ить зомби — обычные приложения этого не делают

**Решение:** использовать `tini` как PID 1:

```dockerfile
FROM python:3.12
RUN apt-get install -y tini
ENTRYPOINT ["/usr/bin/tini", "--", "python", "app.py"]
```

Или флаг Docker: `docker run --init myimage`
