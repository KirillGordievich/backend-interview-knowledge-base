# Web — Производительность

## Ключевые метрики

### Latency (Задержка)

Время от отправки запроса до получения последнего байта ответа. Складывается из:
- Сетевая задержка (RTT — Round Trip Time)
- Время обработки на сервере
- Время передачи ответа

### TTFB (Time To First Byte)

Время от запроса до получения **первого байта** тела ответа. Включает DNS + TCP handshake + TLS handshake + время обработки сервером.

Хорошее TTFB: < 200 мс для большинства случаев (Google PageSpeed: < 800 мс).

### Throughput (Пропускная способность)

Количество данных/запросов, которые система обрабатывает за единицу времени. Измеряется в RPS (requests/sec) или байтах/сек.

### RPS (Requests Per Second)

Количество запросов в секунду — основная метрика нагрузочного тестирования.

```
RPS ≈ (1000 мс / avg_latency_мс) × число_воркеров
```

### Percentile (Перцентиль)

Статистическая мера для анализа распределения задержек.

| Метрика | Смысл |
|---|---|
| p50 (медиана) | 50% запросов завершились быстрее |
| p95 | 5% запросов медленнее этого значения |
| p99 | 1% запросов медленнее — «хвост» распределения |
| p99.9 | 0.1% медленнее |

**Почему среднее обманывает:** если p50 = 10 мс, но p99 = 5000 мс — среднее может быть 60 мс, скрывая что каждый сотый пользователь ждёт 5 секунд.

## Event Loop Lag

Event loop lag — задержка между готовностью callback и его реальным выполнением. Возникает при CPU-bound операциях или переполненной очереди.

```python
import asyncio
import time

async def check_event_loop_lag():
    """Мониторинг задержки event loop"""
    while True:
        before = time.monotonic()
        await asyncio.sleep(0)          # отдать управление event loop
        lag = time.monotonic() - before
        if lag > 0.05:                  # > 50ms — тревога
            print(f"Event loop lag: {lag * 1000:.1f}ms")
        await asyncio.sleep(1)
```

**Последствия:** все ожидающие в event loop запросы замирают пока не завершится блокирующая операция.

**Решение:**
```python
# Блокирующую операцию вынести в executor
result = await loop.run_in_executor(None, blocking_cpu_function, data)

# Или использовать asyncio.to_thread (Python 3.9+)
result = await asyncio.to_thread(blocking_cpu_function, data)
```

## Sticky Sessions (Липкие сессии)

Балансировщик нагрузки направляет повторные запросы от одного клиента всегда на один сервер.

**Зачем:** если состояние сессии хранится в памяти конкретного сервера.

**Реализация:** по IP-адресу клиента или cookie (`JSESSIONID`, `backend` в nginx).

**Проблемы:**
- Неравномерная нагрузка — один сервер перегружен, другой простаивает
- При падении сервера — все сессии теряются
- Горизонтальное масштабирование усложняется

**Правильный подход:** сделать серверы **stateless** — хранить сессии централизованно в Redis. Тогда любой сервер может обслужить любой запрос.
